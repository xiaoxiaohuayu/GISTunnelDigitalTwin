# 隧道数字孪生视频还原方案

版本：2026-10-20，供用户审阅及后续 AI 接手。

## 1. 目标与当前阶段

以当前目录的视频为主要参考，优先实现 Web 隧道数字孪生，追求画面、模型、布局、交互和展示流程的 1:1 还原，同时具备 GIS 地图功能。Blender 用于建模与资产处理。

本轮只分析视频、形成需求和实施方案。用户审阅方案后才开始应用开发。本目录内的抽帧图片属于分析材料，不是应用成果。

“1:1”是目标，不能仅凭一段压缩视频承诺像素级一致。缺少原工程、模型、贴图、字体和相机参数时，需要通过人工重建和同视角截图逐项收敛。真实地理位置和工程尺寸必须另有资料支持。

阅读顺序：

1. 本文：项目范围、技术选择、建模及实施验收。
2. [视频逐段分析](video-analysis/视频逐段分析.md)：时间线、11 类设备、12 类事件、GIS 和看板证据。
3. [AI 接手说明](AI接手说明.md)：后续执行约束、任务顺序和交付要求。

## 2. 视频说明与证据标准

源文件：[本地参考视频](../video_零基础也能做的隧道数字孪生一体化..._0.mp4)。画面为 1280×720，约 30 fps，时长约 105.40 秒。

分析覆盖全片，每秒抽取一帧，共 105 张，并辅以每 3 秒联系表和重点原尺寸截图。文字依据画面及内嵌中文字幕识读，没有单独转录音轨。抽样可能遗漏不足一秒的动作；具体过渡需要在实现时逐段回看原视频。

本文和分析表采用以下证据级别：

| 标记 | 含义 | 如何处理 |
| --- | --- | --- |
| A 画面确认 | 能看到模型、布局或动作 | 纳入还原基线 |
| B 入口确认 | 菜单或按钮存在，但效果未充分展示 | 还原入口，细节按证据补齐 |
| C 解说提及 | 字幕解说提到，未演示完整流程 | 不当作已展示业务模块 |
| D 实施建议 | 为 Web 可用性和后续接入提出 | 与视频事实区分，供审阅 |
| U 待确认 | 小字、含义或真实数据无法确定 | 记录原图和缺口，禁止编造 |

## 3. 还原范围

基线包括以下内容：

- 双洞隧道入口、山体植被、洞外道路、管理建筑、挡墙、护栏、龙门架及洞内道路设备。
- 青色科技风界面、中央标题、左右分类菜单、底部导航与黄色选中态。
- 设备分类定位、场景点位标注、相机飞行、事件定位和红色事件提示。
- 视频中出现的车辆行驶、违停/拥堵演示、落石、施工、风机故障高亮、车辆火焰、洞内侧向展示。
- 入口视角、行车入口、漫游，以及保持三维场景运行的数据看板模式。
- 独立 GIS 页面、地球至区域飞行、双向线路、摄像头点位、上下两行共 16 个监控格、返回场景。
- 龙门架摄像头粉红色覆盖体、路面白色检测区域、设备引线标签。

下列能力不应混入“视频已实现”的清单：

- 真实 AI 视频事件识别、真实传感器采集、生产设备控制。
- 完整工单闭环、告警审核、应急预案调度、历史回放、报表导出、用户权限。
- 结构健康监测算法、自动照明通风联动策略。
- 可视化搭建编辑器、低代码平台和导出客户端的完整产品。

视频解说中出现部分上述方向，但本项目当前目标是还原演示系统。若以后接入真实业务，另列范围和验收条件。

## 4. 页面与交互设计

### 4.1 主场景

中央保留最大的三维观察区域。左侧按原顺序列出 11 类设备，右侧按原顺序列出 12 类事件，具体名称和观察情况见逐段分析。不要把它们替换成通用资产树和后台表格。

选中设备时，菜单变黄，定位对应设备或设备分布区域。显示相关点位和必要标签。多实例设备先展示分布，再允许选单个实例，此处属于实施建议。视频未展示统一的参数详情弹窗，首版不强加复杂弹窗。

选中事件时，先切换或激活该演示场景，再飞向事件位置。红色提示卡和引线需要跟随三维位置；相机变化后仍能指向目标。风机故障需复制黄色高亮，火灾需复制车辆局部火焰和红光。

建议事件切换互斥，清除上一个演示留下的车辆、障碍和特效。让用户连续点击不同菜单时仍能回到可理解的场景。不要复制视频里的车辆穿插、穿模或瞬间黑屏。

### 4.2 底部导航

| 入口 | 视频依据 | 首版处理 |
| --- | --- | --- |
| 隧道入口 | 按钮可见，存在入口视角 | 恢复标定好的入口相机 |
| 行车 | 按钮可见，具体触发过程不够明确 | 保留入口；建议车辆跟随视角，须在实现前回看确认 |
| 漫游 | 约 63 秒后选中，镜头沿入口道路前进并检查设施 | 还原相机路径，建议补暂停、继续、退出 |
| 数据看板 | 约 90 秒后左右变为统计面板，三维仍运行 | 切换 HUD 模式，保留三维和底部导航 |
| 橙色小图标 | 行车与漫游之间可见，含义不清 | 按外观登记；不臆定功能 |

GIS 页面确实存在，但从视频无法可靠判断进入 GIS 的具体按钮。功能上需提供可发现的地图入口，位置先作为待审阅设计项；不能宣称视频已经证明某个未识别图标的含义。

### 4.3 GIS 页面

还原地球飞行至隧道所在区域的过程、卫星影像和起伏地形。两条线路分别以绿、黄表示，上面有蓝色摄像头图钉。地图不能用静态背景图替代，至少支持缩放、旋转、平移、线路和点位定位。

上下各 8 格摄像头画面，桩号和排列见分析文档。两侧方向统计区包含总车流和车型分类。方向名称与部分分类小字待核对，不凭截图猜实际隧道名称。

摄像头格在视频中有黑屏，但无法断言是离线。实施时明确区分加载中、播放中、无信号、播放失败。摄像头点位与监控格通过同一个 cameraId 关联。点格放大、选点高亮属于建议交互，视频没有完整演示。

视频出现 K2+550，只能证明这一桩号出现在界面，不能据此认定真实隧道长 2.55 km。

### 4.4 数据看板

保持视频中的分区和视觉比例：

| 左侧 | 右侧 |
| --- | --- |
| 流量监测：上/下行昨日累计、实时计数和折线图 | 实时事件：事件时间、事件内容 |
| 隧道环境监测：六个指标位置 | 事件类型：环图及数字计数 |
| 隧道设备监测：分组柱图 | 实时路况：环图与轻/中/重度拥堵里程 |
|  | 重点车辆：今日累计与四类车辆图标 |

流量累计栏能辨认“昨日累计”，不要统一改成“今日”。环境指标可辨认水位、洞外光照、洞内光照；其余气体名称和单位存在识读不确定性，见原图，不作为已确认数据定义。示例数值可能存在演示性或单位不一致，不能直接当作真实监测标准。

图表应由结构化数据绘制。演示数据需要有明确来源标识；切换为真实数据后同时替换单位、时间窗口和聚合逻辑。

## 5. 推荐技术方案

### 5.1 首选 Web 架构

建议 Vue 3 + TypeScript + Vite 负责界面，Three.js 负责精细隧道场景，CesiumJS 负责独立 GIS 页面，ECharts 负责统计图表，Blender 负责模型制作。初期本地演示数据即可，不提前建设大而全的后台。

| 选择 | 适合本项目的原因 | 代价 |
| --- | --- | --- |
| Three.js + 独立 Cesium 页面，推荐 | 洞内灯光、设备高亮、车流和特效易控制；GIS 保留完整地球能力；接近视频两种场景切换 | 需要统一两边的 ID 和坐标映射 |
| 全部 Cesium | 地图与工程模型坐标一致，切换较少 | 精细洞内表现、遮挡裁切与特效仍需定制 |
| Unity 客户端 | 可使用成熟场景编辑和渲染工具 | 安装分发和 Web 目标有额外成本，客户端也有 GPU/内存限制 |

先使用 WebGL2 路线，在目标浏览器实测。WebGPU 可以后续评估，不作为首版运行前提。暂不采用 Three.js/Cesium 双画布实时叠加同步方案，视频的独立 GIS 模式不需要这项复杂度。

三维与地图切换时只让当前引擎持续渲染。保留必要的轻量状态；资源压力大时释放非活动场景的 GPU 资源。返回时恢复相机、选中设备或事件，不重新生成整套业务状态。

### 5.2 数据与渲染职责

界面状态、业务数据与模型节点分离，但不引入多余框架。初期需要以下几类数据文件或接口契约：

| 数据 | 必要内容 |
| --- | --- |
| 隧道及线路 | tunnelId、direction、中心线、起算桩号、geoAnchor、坐标系和高程基准 |
| 设备 | deviceId、type、名称、方向、桩号、局部位置、模型节点、状态、相机预设 |
| 摄像头 | cameraId、deviceId、桩号、覆盖参数、流地址引用、播放状态 |
| 事件 | eventId、type、发生时间、位置、关联设备/车辆、展示预设、描述、source |
| 监测值 | deviceId、metricCode、value、unit、sampledAt、quality、source |
| 车辆 | vehicleId、车型、车道、沿线路里程、速度、运行状态 |
| 相机预设 | presetId、position、target、视场角、过渡时长、关联对象 |

source 至少区分 simulation 和 live。位置同时携带方向与桩号，不能只凭“K0+100”确定唯一设备。气体浓度等单位应由指标定义给出，禁止把所有数值统一写成 ppm。

演示阶段用固定随机种子或预置时间序列，使同一场景可重复截图验收。事故专用车辆与背景车流分开管理，避免切换事件时留下残余对象。

## 6. 坐标与 GIS 对齐

真实地理信息缺失时，先重建视频的相对布局，并标记“演示位置”。不要给未知隧道绑定看似真实的经纬度。

获得资料后，采用 WGS84 地理锚点与局部 ENU 米制工程坐标。记录影像服务坐标系、工程源坐标系、高程基准和转换方法。国内地图服务若使用其他坐标体系，需明确转换，不能靠人工拖拽掩盖偏移。

Blender 按米建模，应用缩放。Blender 的 Z 向上与 glTF 的 Y 向上通过导出及统一加载转换处理，避免多次旋转。业务层保留一个明确的工程坐标约定，模型根节点负责到渲染坐标的变换。

双向线路各自保存中心线与里程方向。设备位置可由中心线里程、横向偏移、高度表示，再转换成模型和地图坐标。用至少三个已知控制点验证位置、比例、方向；高程需要单独检查。

地图中地下隧道展示采用线路覆盖为基线。若需要展示地下实体，再增加地形透明或裁切。Cesium 支持相关能力，但不能仅靠关闭地形深度测试完成正确的地下遮挡。

## 7. Blender 资产计划

### 7.1 建模清单

| 资产组 | 必须观察和匹配的细节 |
| --- | --- |
| 山体与洞口 | 双洞相对高度、间距、洞门轮廓、山坡坡度、裸岩、草地树木 |
| 洞外道路 | 道路走向、双车道比例、虚实线、路肩、护栏、黑黄隔离带、白色挡墙 |
| 管理区 | 左侧粉色/米色建筑、屋顶和立面、与道路位置关系 |
| 隧道内部 | 拱形断面、墙面/路面色彩、灯具间距、线缆或支架可见部分、明暗节奏 |
| 门架及设备 | 情报板文字、信号灯、车道指示、摄像头、环境监测、电话、消防、风机、控制柜、限速牌 |
| 车辆 | 多色轿车、货车、客车/厢式车等外形层次，尺寸和道路比例 |
| 事件道具 | 落石、施工围挡、作业车辆、人员；抛洒物外观需补证据 |
| 动态覆盖 | 检测区白线、粉红检测体、点位和引线由引擎生成，参数绑定设备 |

第一个可审阅样板必须同时包含一个入口全景和一段洞内，验证建筑、山体、隧道断面、灯光及 UI 的匹配程度。只有通用隧道管道模型不足以验收。

### 7.2 文件和导出规范

- 保留可编辑 .blend 源文件、贴图及导出说明，运行时使用 GLB/glTF。
- 按入口区、洞内区段、设备原型、车辆和事件道具拆分。区段长度由可见范围与加载测试决定，不先拼成一个超大文件。
- 节点命名稳定，例如 DEV_FAN_001、DEV_CAMERA_001。业务 ID 与节点映射单独记录，不能依赖易变的数组序号。
- 重复树木、灯具和设备复用几何体及材质；给远景植被和山体准备较低细节版本。
- 使用可导出的 PBR 材质和纹理。Blender 程序化节点、合成效果、体积效果不保证自动转换到网页。
- 烘焙 AO/法线及必要照明纹理，网页验证后再批量制作。光照贴图需要在运行时明确加载配置，不能假定 GLB 自动保留 Blender 全部灯光效果。
- 洞内灯具以自发光材质、烘焙效果为主，少量实时灯光辅助。不要为每盏灯开启动态阴影。
- 压缩采用实测后的 Meshopt 或 Draco，以及 KTX2 纹理；配置对应解码器。压缩后检查灯牌文字、法线、透明体和边缘质量。

## 8. 关键业务实现约定

设备定位、事件展示、漫游和车流分别持有状态。相机控制只有一个当前拥有者。开始事件定位时停止当前自动漫游，用户手动操作时允许取消飞行，防止多个动画争抢相机。

车流沿车道中心线移动，速度按时间差计算，车辆保持合理间距。视频演示不能证明交通仿真模型；首版只需可重复的展示车流，无需引入完整交通仿真平台。

施工、落石、违停、拥堵等使用独立演示配置。火焰采用局部粒子或序列帧与受控光晕。烟雾、行人和抛洒物的具体外观尚缺充分证据，先作为待补素材项，避免用未经确认的特效替代原效果。

若需真实业务，后续再增加“产生、确认、处置、解除”等事件状态及审计记录。当前视频没有证明这套流程。真实风机/照明控制必须经服务端权限、指令回执和设备状态校验，不能把前端改色当成控制成功。

### 8.1 视频流接入

浏览器不能直接把 RTSP 地址放进 video 播放。真实摄像头应通过网关转换为浏览器支持的 WebRTC 或 HLS 等形式，按延迟目标和现有系统选择。

16 格默认使用子码流，选中时再加载高分辨率。具体分辨率、帧率和同时解码数量以目标电脑实测为准。共享相同来源时避免无意义重复拉流。离开 GIS 页面停止或暂停流，重连限制退避，失败显示状态。

没有真实流时，可用有授权的本地样片演示，并标明“演示视频”。不能把循环片段称为实时监控。

### 8.2 真实数据接入的后续边界

演示版先用前端适配器读取本地数据。真实接入阶段根据已有平台选择服务端语言，不提前限制 Java、Node.js 或 Python。服务端负责协议适配、身份校验、聚合和推送；前端不持有摄像头或设备平台凭据。

实时值和事件通过 WebSocket/SSE 等推送方式更新，历史查询另走接口。更新时间、数据质量和断线状态应可见。统计按真实事件/流量口径计算，不复制视频里的演示计数作为业务事实。

## 9. 性能与视觉验收

以下是建议目标，尚未经过本机原型测试，不能当成已达成性能。

| 项目 | 建议验收方式 |
| --- | --- |
| 基准环境 | 记录电脑型号、GPU/内存、浏览器版本、分辨率、DPR、网络条件 |
| 帧率 | 1920×1080 常用场景目标 60 fps，最低目标 30 fps；含事件和看板的连续漫游测试 |
| 视频压力 | 单独测试 16 格视频与地图同开，不用无视频结果代替 |
| 首屏 | 样板阶段测定传输体积和首个可操作时间，再约定固定预算；不一次下载所有洞内资源 |
| 内存 | 连续切换地图/三维 20 次，监测内存及 GPU 资源是否持续增长 |
| 大屏 | 1280×720 对齐参考，1920×1080 检查文字可读与布局比例；不强求首版手机端 |
| 异常 | 模型加载失败、视频不可用、数据断连均有明确状态，不能停留在黑屏 |

视觉验收使用固定演示数据、同一相机预设和关闭随机漂移的场景截图。至少对照入口、洞内设备、风机故障、施工、火灾、GIS 和数据看板七组参考。

检查顺序为轮廓和空间比例、相机视角、UI 位置与尺寸、材质灯光、动态效果、文字图标。先解决几何及构图，再微调发光。建议每组输出参考图、实现图和差异说明；相机匹配后再讨论像素差异，录屏压缩和水印区域应排除。

必过功能检查：

- 11 个设备入口和 12 个事件入口顺序正确；每个都有可解释的响应，证据不足项明确列出。
- 设备和事件标注不因旋转相机而偏离目标，不被菜单遮住关键信息。
- 漫游可进入和退出；相机切换连续，无穿山、瞬黑和飞出场景。
- GIS 有真实交互地图、两条线路、摄像头点位、16 格布局和返回场景。
- 看板与三维同时工作，菜单模式切换正确，统计口径和单位有定义。
- 视频原有水印、字幕、录屏提示不纳入产品 UI，视频穿模与车辆重叠不纳入验收要求。

| 阶段 | 工作 | 可审阅交付与通过条件 |

## 11. 缺失资料及处理方式

| 缺口 | 影响 | 当前可推进方式 |
| --- | --- | --- |
| 原模型、贴图、字体、UI 图标 | 影响精确外观与制作工作量 | 依据参考重建，记录偏差；原资产能提供时优先复用 |
| 隧道名称、经纬度、线形及高程 | 无法确认真实 GIS 对齐 | 先做演示地理锚点，明确标识；不宣称真实工程定位 |
| 尺寸、设备布置和桩号表 | 不能从透视画面恢复工程精度 | 用相对比例建模，后续用工程资料标定 |
| 未看清的指标、方向名称和小字 | 影响文字 1:1 | 保留截图和 U 标记，不擅自替换成行业常见字段 |
| 实际传感器/监控接口 | 影响实时接入 | 演示适配器先行，真实接入单列 |
| GIS 入口及橙色图标含义 | 影响精确交互路径 | 实现前回看原片，必要时请用户确认这两项 |

这些缺口不阻止制作视觉样板，但会限制“真实工程一致”与严格 1:1 的最终结论。
